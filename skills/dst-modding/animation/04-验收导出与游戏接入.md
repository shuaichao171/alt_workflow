# 04 验收导出与游戏接入

原则：按“文件完整 -> 静态外观 -> 骨骼动作 -> 视觉预览 -> SCML 源文件与编译包交付 -> 游戏运行”分层验收。前一层通过不能代替后一层。

2026-09-07 明确的最终交付要求：**必须交付 SCML + 全部引用 PNG，以及官方 Mod Tools 实际编译的饥荒动画包 `anim/*.zip`。** 网页和工程压缩包只是验收、编辑与归档材料，不能被称作已打包的游戏动画资源。

## 0. 批量制作前的 P0 技术小样

在 G2 部件方案明确后，先做代表性部件的小规模装配，不必等全部拆件或全部动作完成。目的不是提前完成美术验收，而是证明选定的骨骼、导出、编译与加载方法可行。

1. 选一个个体，制作一个循环和一个单次短动作，覆盖 `side/down/up` 及左向镜像。保留真实骨骼，包含本轮会用到的 IK、脚掌 Transform、缩放继承和层级变化；计划换图或显隐时，小样也必须包含对应测试。
2. 按第 5 节导出 SCML/PNG，检查原生与 SCML 重建画面。记录实际支持的功能、时间映射及误差，不通过的功能先修适配器或调整制作方案，不能静默丢弃。
3. 根据当前安装版本的官方说明确认调用方式，用官方 Mod Tools 在独立输出目录真正编译并检查样包。必须从最终 `anim.bin` 核实每段实际为 30 FPS，核对帧数、时长、姿势和事件；涉及重采样或中间数据适配时，按第 6 节验证。保存源/产物哈希、工具与依赖版本、脚本版本、完整命令、工作目录、退出码和日志；成功后才将命令写成可复用构建说明，不能把未运行参数标为已验证。
4. 在已确认授权的隔离测试模组和测试世界中加载样包，使用独立资源命名或其他明确的隔离方式，避免与正式资源冲突。检查方向、比例、原点、循环/单次播放与事件时间，保留游戏画面和日志；不得覆盖正式动画包、修改用户存档，或为通过小样删除正式 StateGraph 的动作调用。
5. 在新的空输出目录用同一源和记录的命令重建一次，核对动作/方向/帧数、纹理依赖和画面，排除旧产物缓存。ZIP 的打包时间等非语义元数据可能变化，不能只用 ZIP 字节相同或不同代替内容核验。

P0 通过条件是上述适用项目全部有成功证据；它只验证小样能力，不替代全量 G5、G6、G7。工具构建、导出规则或关键附件类型变化后重跑受影响小样。游戏测试未获授权或本轮只做中间阶段时记录“未执行”和风险，不擅自启动软件；按用户明确范围继续不等于 P0 通过。

记录字段见 06 第 8 节。本节是批量制作前的执行要求；没有实际跑过 P0 的项目必须记录未执行项与风险，不能写成已通过。

## 1. 文件与结构检查

- 每个个体有自己的工程、部件和动作，不串用其他个体的贴图。
- PNG 存在、能解码、尺寸正确、透明边完整；按清单检查缺件和重复件。
- 骨骼父子关系、槽、附件、约束目标和关键帧引用闭合。
- 当前方向外的附件正确隐藏，原生 `side` 朝右，完整镜像得到左面。
- 用 OpenSpine 原生验证结果核对实际工程，不只检查自定义生成器写出的字段。
- 保存再加载，比较同一时间的实际骨骼矩阵和附件顶点，确认保存没有改变动作。

## 2. 动作逐帧检查

人形行走、攻击和死亡必须增加以下专项门槛：正常人形行走采用左右同幅、错开半周期的迈步节奏；左右脚的可见接触、抬起和前后位置必须交替。不能只凭相位公式成立或只移动根骨就宣布步态通过；还要检查两脚初始位置、落脚高度与遮挡是否让交替在画面上可见；攻击必须逐方向核对用户指定的挥击路径（例如上方挥杖），不能以单位类别或旧模板替代意图；死亡必须检查鞋/脚与骨盆、躯干的可见连接，隐藏腿骨或 IK 目标存在不等于身体已经连上脚。审查对象是活动骨分支的世界矩阵、附件顶点、alpha 轮廓和绘制顺序的组合。

技术数值检查失败后，不得通过降低阈值、改用更宽松的单位或删除异常帧来“降格通过”。若姿势模型改变导致原门槛不适用，先更新动作规格并说明理由，再以新规格重跑；旧结果保留为失败证据。数值检查通过也不能替代接触表和 1x 尺寸人工审查。

| 检查项 | 检查方式 | 有问题时回到哪里 |
|---|---|---|
| 接缝和穿层 | 关键姿势放大看，同时看 1x 游戏尺寸 | 拆件绘画、pivot 或槽层级 |
| 脚滑和支撑 | 对照足端轨迹、支撑阶段和重心 | IK 目标、身体曲线、步态 |
| IK 可达性 | 目标与求解端点距离、异常伸直或翻折 | 骨长、目标、身体高度 |
| 攻击意图 | 蓄力、命中、回收与 Lua 事件对照 | 关键姿势和时序 |
| 换图可见尺寸 | 同尺度比较轮廓与关节锚点，检查附件、骨骼和继承缩放叠加 | 换图基础尺寸、语义锚点和动作强调幅度 |
| 循环连续 | 首尾矩阵、相邻帧运动趋势、持续播放 | 周期、关键帧曲线、导出端点 |
| 死亡接地 | 附件变换后的实体轮廓、主躯干与地面关系 | 倒地姿势和根部关键帧 |
| 死亡保持 | 末段矩阵、末姿是否回弹或漂移 | 保持段和播放循环设置 |
| 四方向一致 | left/right/down/up 同步对照 | 完整镜像、显隐、分向姿势 |
| 渲染完整 | 空白帧、裁边、异常分离块、透明通道 | 原生导出范围与附件 |

不能把透明画布底边或投影最低像素当作实际地面。也不能把矩阵首尾相同当作速度连续的证明。自动连通性检查可以发现明显脱节，但发现不了所有硬接缝和造型问题，必须看实图。

修改动作后重新原生采样和导出；修复应落在可编辑工程中，不只修预览视频。

二维投影角、接缝连通性、全图相似度各有适用边界，不能用其中一项通过替代姿态与遮挡的视觉审查。

### 2.1 局部修复与回归门槛

1. 修改前冻结只读基准，记录工程、PNG、采样数据、导出脚本和工具构建的版本及哈希；先保留手改工程，不运行可能覆盖它的历史重建入口。
2. 列出允许修改的个体、方向、动作、部件/骨骼、属性与时间段，并单列必须保持的首末姿势、事件、时长和脚踝目标。若涉及共享 setup、骨长、约束或贴图，先扩大影响清单并说明原因，不能继续称作仅改单条动作。
3. 对未授权修改的动画比较语义轨道、时长、循环、事件、附件引用和层级；对共用 PNG 比较 SHA-256。JSON 格式化变化与动作变化分开报告。
4. 用相同采样构建、时间点和坐标系比较基准与修订版的实际骨骼矩阵、附件顶点和原生 PNG。数值容差与单位在比较前确定，记录最大误差、所在帧和骨骼；必须改变工具构建时，保留原记录，并用新构建另采样基准和修订版，不能混用求解器直接归因于动画修改。
5. 目标片段做专项逐帧检查；全量个体/方向/动作检查遗漏、空白、裁边和循环。依照第 5 节重导出并核对 SCML，已进入 G6 的交付还须重编译验包；对照图使用实际渲染，不用有损 MP4 的逐字节差异判定动画回归。
6. 允许范围外有未解释变化，或原问题未修好，就不能通过回归。没有可用基准时写“未验证不变性”，不能声称其他动作完全不变。最终记录视觉审查与用户结论，不以矩阵通过代替它们。

若批准改变多个动作共用的起始/收尾姿势，明确区分“首末闭合、两动作入口一致”和“首末与旧版完全相同”。若批准某部件越过原有层级（如手臂越过头部），未修改部件的全局层号可能随之重排；检查它们之间的相对绘制顺序，并记录被允许的前后关系变化。

允许范围必须逐次写明，例如“只允许某个体某方向的攻击腿部轨道变化，其余动作、方向和全部 PNG 保持”。目标片段内的身体、头尾、事件和首末可见姿势同样要核对；该范围来自本次修订记录，不是后续修改的默认白名单。

## 3. 导出设置与数量

- 母版、原生采样、预览和最终动画采用 30 FPS；显式记录采样配置及媒体实测时基。MP4 使用 30 FPS，HTML 以 `F / 30` 秒推进；APNG 等按格式精度记录帧时长，GIF 等时间精度不足的媒体仅作辅助预览，不能单独证明精确 30 FPS。
- 固定每段画布和原点，范围覆盖该动作全部姿势，避免逐帧裁切造成抖动或裁边。
- 各动作保留同一角色世界原点、尺度和地面约定；跨状态对照用固定相机与共同画布，不能各自居中掩盖首末姿势或根部位置跳变。
- 原生 PNG 序列保留透明通道；透明动画可另交 APNG，浏览器审查另交 MP4。
- 循环动作保留闭合关键帧，但不重复导出与首帧相同的末端帧。
- 攻击、死亡等单次动作保留必要的最终帧；死亡关闭循环。
- 骨架叠加图与成品贴图动画分开提供，说明叠加数据来自实际骨骼矩阵。

每段的实际 PNG 数由该段总帧数和循环端点规则决定，逐段记录：循环段导出 F0—F(N−1) 共 N 帧，单次动作另记最后姿势时间、导出张数和保持时长。帧数、最后关键帧时间和媒体编码时长不是一回事，记录时分栏填写。

## 4. 提交给用户的验收包

G5 阶段视觉验收包至少包含以下内容。它不是 G6 最终资产交付；最终必交项见第 6 节。

1. 每个个体一个独立可编辑工程，以及全部引用 PNG 和必要伴随状态文件。
2. 每个个体、每种动作的四方向同步预览，能暂停、逐帧、拖动时间和重播死亡。
3. 关键姿势接触表、骨架与 IK 目标示意、必要的浅深背景检查图。
4. 动作名、方向、FPS、循环方式、攻击和落地事件表。
5. 文件清单、检查结果、工具版本、已知问题和用户验收状态。
6. 实际使用的生成、导出和验证脚本；注明外部依赖和会覆盖的输出。

预览页尽量离线可打开。桌面和手机尺寸都检查媒体加载、文字遮挡、控件、实际非空画面与控制台错误。验证后关闭本任务启动的测试浏览器，不动用户原有窗口。

提交入口时还必须：

- 核对最新版本目录，不继续发送旧修订版链接。
- 用修订版本或内容哈希同步更新帧图、关节叠加数据与网页缓存标识；旧截图和报告保留为历史记录，不作为最新验收图混入交付。
- 同时给出不带 `#` 页内参数的实际 HTML 文件路径和独立 MP4/APNG/GIF 或关键帧图；深链接只作为额外入口。
- 区分“文件存在”“自动化测试通过”“用户实际能打开”。打开工具仅返回排队状态时，不能写成已打开。
- 用户反馈失败时询问是链接无响应、路径错误还是媒体加载失败；记录实际错误。浏览器安全策略拦截时停止受限的自动打开，不通过改地址、代理或更换控制方式绕过。

工程归档打包后检查 ZIP CRC、清单和逐文件 SHA-256。明确哪些文件在压缩包内、哪些只保存在项目工作区，以及原生帧序列是否装入归档。此 ZIP 不是第 6 节的游戏动画包。

## 5. SCML 转换

如果当前 OpenSpine 版本没有原生 SCML/Klei 导出，使用以下转换链：

```text
OpenSpine 可编辑骨骼工程
  -> 原生逐帧求解的附件矩阵
  -> 烘焙对象变换和层级的 SCML + 全部引用 PNG
  -> 官方 Mod Tools 编译并交付游戏 anim/*.zip
  -> 游戏运行验证
```

可编辑母版必须保留骨骼。烘焙 SCML 没有 `bone_ref` 不等于没用骨骼制作；也不能反过来把烘焙对象轨道称为原生可编辑骨架。

制作 SCML 时使用 XML API 或既有工具，不手工拼接 XML 字符串。检查 folder/file、mainline/object_ref、timeline/key 引用、z_index、PNG 尺寸、安全相对路径与时间网格。允许有依据的负缩放和非中心 pivot，不做机械“归正”。

**新项目时间换算必须从 30 Hz 的绝对帧号出发。** 母版和原生采样的 `t(F) = F / 30` 秒；SCML 使用整数毫秒时，对每个帧号分别计算 `time_ms(F) = round(F × 1000 / 30)`。例如 F0/F1/F2/F3 对应 0/33/67/100 ms，F12 = 400 ms，F15 = 500 ms，F30 = 1000 ms。间隔为 33 或 34 ms 是有意量化，不能累计 `F × 33`；固定 33 ms 不等于精确 30 FPS。逐帧四舍五入误差至多 0.5 ms，不随动作长度累积。循环长度、单次末姿及事件时间使用同一换算，保留源帧号和量化误差表；编译结果仍须满足最终 30 Hz。

固定 33 ms 网格会累积误差：同一帧号在母版和 SCML 中会出现毫秒级偏差，动作越长偏差越大。必须逐帧用 `round(F × 1000 / 30)` 换算，不累计常数。编译接入仍须对照可见命中姿势与 Lua 伤害时刻；事件是否循环或触发由实际运行时代码决定。

分析器示例，仅检查交付源文件：

```powershell
# 从待验收动画项目的根目录执行；分析器由环境单独提供。
$ProjectRoot = (Get-Location).Path
$Revision = "your-revision"
$Analyzer = $env:DST_SCML_ANALYZER
$Projects = Join-Path $ProjectRoot "delivery\$Revision\source"
if ([string]::IsNullOrWhiteSpace($Analyzer)) { throw "请先设置 DST_SCML_ANALYZER" }
python "$Analyzer" "$Projects"
```

### 5.1 导出功能边界

下表约束本项目的转换链，不代表所有 SCML 工具具有相同能力。先在 P0 中为实际用到的功能建立小样；未验证的功能不能当成支持。

| 功能 | 制作与导出要求 |
|---|---|
| Region 图片、旋转、缩放、镜像及 pivot | 对照附件变换后的四角与锚点，检查负缩放和角度组合；不能只验证图片中心 |
| 剪切及非均匀缩放继承 | 父子旋转与非均匀缩放可能产生不能由当前对象变换准确表达的剪切。现有脚本以归一化轴点积衡量正交误差，超过 `0.002` 会报错；这是当前适配器门槛，不是通用像素容差。超限先修 rig 或明确批准的附件烘焙方案，不能删掉断言直接交付 |
| 附件显隐与换图 | 显隐应通过对象进入/退出 mainline，换图通过 folder/file 引用变化表达。当前脚本只从首帧槽列表建轨道，文件清单也按现有三方向同名部件组织；新增晚出现的槽或闭眼等换图 PNG 时，必须先扩展清单/时间线处理并测试，不能只补图片就声称可导出 |
| 动态层级 | 每帧核对 object_ref 和 `z_index` 与实际遮挡一致；测试手脚交叉、远侧腿显露、尾巴转入身体后方的前后帧 |
| 透明度、颜色、混合与网格变形 | 当前适配器没有通用的动态颜色/alpha 或 mesh/deform 支持。需要时先验证并实现转换，或经确认改为兼容的状态附件；不能把原生预览中的效果静默漏掉，也不能把网格当作普通四角图片处理 |

导出适配脚本由项目自行提供，不随本仓库分发；本流程只记录它需要满足的能力边界。脚本会写出源文件，失败时已有部分输出也不能用于交付。新增功能须连同小样与导出测试一起更新。

### 5.2 原生、SCML 与编译后画面对照

1. 冻结相同源版本、附件和显示尺度，先填写锚点/附件顶点的像素容差、角度容差及事件时间误差上限，记录坐标单位和依据；未填写或结果出来后临时放宽，都不能据此判为通过。
2. 在 OpenSpine 原生输出之外，独立解析导出的 SCML 对象轨道重建画面，或用经验证的 SCML 播放器渲染。不能复用原生 trace 再画一遍，并把它称作 SCML 验证。
3. 用同一物理时刻建立采样对应表，注明源时间、SCML 时间及量化误差，不简单按同名 F15 当作完全同步。对照首帧、蓄力、命中、回收、最大抬腿、层级/换图切换前后帧、循环边界和死亡保持段；数值检查覆盖全段，图片至少覆盖这些高风险时刻。
4. 保留共同画布、地面、相机与缩放，输出并排图、叠加差异图和测量报告。缺件、错图、穿层、镜像错误、事件错位或超出已定容差必须修复；抗锯齿或纹理压缩差异单独解释，不能用宽松全图相似度掩盖局部脚掌问题。
5. 编译后从最终包读取实际动作/build/纹理，使用可用且经验证的解码/渲染工具检查，最终还要在游戏中对照轮廓、锚点和关键姿势。没有可用的编译包渲染工具时，写明“编译包结构已查、游戏画面对照待 G7”，不要拿原生视频冒充游戏成品。

G6 至少完成原生与 SCML 的对照、编译包内容核验并单列编译后画面对照状态；未游戏实测不能通过 G7，也不能宣称三者保真已全部验证。

### 5.3 游戏实际贴图替换与原点验证

此项适用于人物动作复用、皮肤/装备替换和临时 Build 覆盖。动画存放各部件的变换与层级，Build 提供具体帧的几何、原点和纹理。`Asset("ANIM", ...)` 只声明资源；`PlayAnimation` 也不自动选用动画包内的 Build。工程里动作正常，不能证明换成角色贴图后仍然正常。

**先记录实际显示来源。** 从角色初始化、皮肤/装备逻辑和 StateGraph 查基础 Build、`SetBuild`、`AddOverrideBuild`、`OverrideSymbol`、`OverrideSkinSymbol` 及对应清理。记录进入/循环/退出、受击、移动、攻击、死亡和主客机分支中，活动 symbol 最终由哪个 Build/frame 提供；多种覆盖的优先级按实际调用和游戏结果确认，不凭名称猜测。

按接入契约选择并验证处理方式：

| 接入方式 | 制作/编译要求 | 验证组合 |
|---|---|---|
| 保留角色基础 Build | 用目标角色的实际 symbol/frame 几何适配源动作，保留完整矩阵；在源或中间 XML 中调整后经官方工具编译 | 最终动画 + 实际角色 Build/TEX |
| 动作使用专用 Build/临时覆盖 | 源动作与专用贴图原点匹配；播放前选择/启用覆盖，退出和打断后成对恢复，检查缺图回退 | 最终动画 + 当前有效专用/回退 Build，以及恢复后的角色状态 |
| 装备/皮肤覆盖部分 symbol | 分别记录这些部件的真实来源，检查内容、尺寸、锚点、显隐和覆盖关系 | 最终动画 + 当前各部件实际选中的 Build/frame |

**保留人物与装备图层时，还要完成动画通道适配。** 从同方向的原版动作读取真实装备矩阵和 layer，建立帽子到头部、持物臂到肩部/躯干、持物符号到手部的连续关系。将所需通道逐帧加入 mainline；近侧普通臂与持物臂分别由 `ARM_normal` / `ARM_carry` 控制，避免双臂同时显示或缺臂。原版帽子可能切换 `HEAD` / `HEAD_HAT` 并覆盖 `swap_hat` 或 `headbase_hat`；不要在动作状态中强制 Show/Hide 或清空其他系统拥有的覆盖。测试换装事件发生在进入、循环、退出期间时，最新装备状态能保留到普通待机。

可以将经过适配的源数据导出为只含 `animation.xml` 的官方中间 ZIP，再由官方 `buildanimation.py` 生成仅含 `anim.bin` 的动画包。此时资源不提供专用 Build/TEX，清单必须记录实际依赖的角色与装备资源，不能因包内没有 Build 就跳过几何和纹理验证。存在独立跟随特效、空占位 symbol 或引擎专用头盔交换的装备，离线只能核查已模拟部分，不将缺失覆盖静默回退成角色部件后声称装备验证通过。

**原点补偿的符号必须来自实际顶点定义。** 对已核对的官方 BILD v6，完整图片像素位置为 `(px, py)`（左上角原点，y 向下），画布大小为 `(w, h)`，Build frame 的中心偏移为 `o = (x, y)`。优化后的 atlas 顶点仍服从：

```text
v_build = o + (px - w/2, py - h/2)
v_world = M * v_build + t
M = [[m_a, m_c], [m_b, m_d]]
t = (m_tx, m_ty)
```

官方编译器的 `ExportBuild` / `AddVertsToVB` 使用 `xoff = x - w/2`、`yoff = y - h/2`，不是将中心偏移取反。若源和目标的像素画布已配准，仅中心偏移不同，则保持像素世界位置的平移补偿为：

```text
t_target = t_source + M * (o_source - o_target)
```

最小回归例：`M = I`、`o_source = (0, 0)`、`o_target = (0, -90)` 时，新平移应增加 `(0, 90)`；加上目标 Build 的 `-90` 后才回到原位置。SCML 的 y 轴向上，应用公式前须统一坐标约定。file pivot 与 object pivot 都要核对；完整 2×2 矩阵中的镜像、非均匀缩放及剪切不能在补偿时丢失。图片尺寸、透明画布或实际内容不同，须先做部件配准与语义锚点验证，不能仅套这个平移公式。

**用独立结果验收，避免错误公式自证。**

1. 读取模组中真正安装的动画 ZIP 和全部实际使用的 Build ZIP，检查 CRC、哈希、Build 名称和活动 symbol/frame 覆盖范围；逐个真实帧号及 duration 区间解析，缺失帧明确报错。源目录、暂存目录、清单与安装目录的同名 ZIP 必须核对内容，不能假设一致。
2. 独立解析作者 SCML/原生参考，同时从最终 `anim.bin` 与实际 Build 的优化顶点、UV 和 TEX 重建同帧画面。透明裁边后的 atlas 小块须放回原始画布，不能把裁切图拉伸到整个部件尺寸。
3. 全帧检查顶点/锚点误差，并用共同原点、画布和比例查看首末、换图、蓄力/命中、极限姿态与恢复姿态。测试至少覆盖旋转、镜像及发生原点差异的部件。修复时保留错误组合的对照，证明独立检查确实能发现错位。
4. 核对动画实际发出的 symbol 和 layer 是否与运行时代码/文档一致；隐藏的 SCML 备用时间线不等于游戏中已发出对应装备层。缺失兼容图只有在确认透明、符合契约后才能在临时编译投影中省略，不删除作者源轨道来凑通过。
5. 使用临时覆盖时，验证每段播放前启用、段间交接、正常退出和各类打断后恢复；还要检查恢复时是否仍残留依赖旧 Build 的动画帧。Lua 测试可证明代码调用/清理路径，实际渲染优先级、装备/皮肤组合和主客机显示仍需游戏测试。
6. 原点适配后经官方工具重编译，重跑本节检查并更新最终清单；禁止直接改写最终 `anim.bin` 冒充重新编译。安装后再次核对实际包哈希。记录源码/SCML、原生、编译资源重建、生命周期测试及游戏实测各自结论，不能互相替代。

字段模板见 06 第 1、8.1 和 8.2 节。以上为通用规则和数学示例，不构成任何具体项目已通过的验收记录。

## 6. 最终必须交付 SCML 和编译包

三类文件不可混淆：

| 类型 | 实际内容 | 能否替代最终游戏包 |
|---|---|---|
| 可再生成源文件 | `.scml`、全部相对路径引用 PNG、OpenSpine 骨骼母版和必要伴随文件 | 否，但必须保留并交付 |
| 工程验收归档 | JSON、SCML、图片、预览、文档、脚本等的普通 ZIP | 否；是运输和归档容器 |
| 饥荒运行时动画包 | 经官方 Mod Tools 编译的 `anim/*.zip`，包含实际二进制动画/build 与 TEX 纹理 | 是，仍须核对契约并另做游戏实测 |

完整动画包通常包含 `anim.bin`、`build.bin` 和编译器生成的 `atlas-*.tex` 等纹理。若动画与 build 分包，交付全部依赖包并写明对应关系；不能仅因某包缺少一个文件就一概判错，也不能漏交其依赖。只有 `anim.xml`、`build.xml` 或 PNG 的中间 ZIP 不等于游戏运行时产物。

### 编译前后步骤

1. 冻结本轮源版本并记录 SHA-256，核对 bank、build、entity、动作名、方向、symbol 和消费代码。多外观个体分别明确 build，不默认共用一个名称。
2. 验证 SCML 与全部 PNG；补齐实际调用的动作，包括需要的 `hit`。不要通过删除调用、空动作或旧资源掩盖缺项。
3. 使用官方 Mod Tools 实际编译；安装目录由使用者自行确认，并通过 `DST_MOD_TOOLS_HOME` 环境变量或项目本地配置提供。先核对目录中的实际工具、官方说明和已验证构建脚本；不要假定 Steam 库盘符，也不要只凭 `scml.exe`、`autocompiler.exe` 或 `compiler_scripts` 等文件名猜命令。
4. 将源文件、中间产物和最终 `anim/*.zip` 分目录保存。优先输出到独立交付目录，不未经确认覆盖模组中现有动画包。
5. 保存完整命令、工作目录、工具版本、退出码、日志和实际产物路径。退出码为零仍须检查文件确实产生，时间/哈希对应本轮源，不把旧包当作新结果。
6. 检查最终包 CRC 和内容，逐动作读取 `anim.bin` 中的实际 FPS、帧数及对应时长，确认均为 30 FPS，并核对 bank/build、动作、方向、symbol 与纹理依赖。对照首末、命中、换图和保持段时间，不能只核对文件名或报告中的目标值。必要时解包只用于验证最终包，不把反编译结果回写成制作源工程；SCML 分析通过不能代替编译包检查。
7. 同版交付源工程、全部 PNG、编译好的包、构建/验证记录与清单；任一源或部件修改后重新导出、编译和验包，再更新媒体与哈希。

正式构建应复用 P0 已成功的调用方式，并重新核对当前输入布局、bank/build、依赖与输出位置。将可重复执行的命令、工作目录和工具/脚本版本放入交付说明；未实际跑通的项目仍填“待验证”，不从其他资源的命令推断本项目成功。

### 6.1 官方编译器帧率适配

已实证存在固定输出 40 FPS 的官方 `scml.exe` 链路；这描述已测版本的行为，不推断所有版本相同。每个项目在 P0 记录实际工具版本/哈希、输入时间网格和二进制实测 FPS。若当前工具输出 40 FPS，不能因官方工具默认值而将最终要求改为 40 FPS，也不能把预览改速当作已解决。

需要适配时，可保留官方生成的中间数据，在可审计的适配步骤中按源 30 Hz 时间重新建立动画帧和事件映射，再用官方 `buildanimation.py` 等实际支持的官方编译步骤生成最终二进制。具体命令与中间数据格式必须实测，不能将此方法描述成已经跑通。P0 必须对照适配前源姿势、SCML 和最终编译结果，证明动作时长、首末与关键姿势、命中/换图/层级切换及循环边界在既定容差内保持；保存适配脚本版本、输入/输出哈希和完整日志。

不得直接篡改最终 `anim.bin` 的 FPS 字段、伪造二进制或只更改标称帧率；也不得简单丢帧后跳过姿势与事件验证。无法完成官方 30 FPS 编译与核验时，明确标记“30 FPS 编译未通过，阶段交付”，P0/G6 不得放行。

建议交付结构：

```text
delivery/<revision>/
  source/<individual>/*.scml
  source/<individual>/images/...png
  rig/<individual>/...             OpenSpine 母版、贴图与伴随文件
  compiled/anim/<asset>.zip        真正编译后的游戏动画包
  review/...                       同版预览和接触表
  reports/compile.log
  reports/validation.json
  manifest.json                    源/产物哈希、工具、版本、命名和依赖
  README.md                        安装映射、资源声明、验证状态
```

G6 完成条件是源工程齐全、原生与 SCML 对照通过、真实编译成功、编译包检查通过并已交付，且编译后画面对照状态明确。编译失败或缺工具时记录阻塞和日志，明确标记“阶段预览，最终交付未完成”，不能只交网页、视频或工程 ZIP 后宣告完成。

## 7. 游戏接入与实测

接入前先记录已有代码契约，字段包括 bank、build/entity、方向数、被调用的动作名、攻击命中事件及其时间、超时或冷却等。未确认的字段写“待确认”，不要按通用模板猜一个名字填上。

正式接入前必须：

1. 完成用户视觉验收，解决影响动作的剩余素材问题。
2. 补齐所有被代码调用的动作（例如受击 `hit`），确认是否还需要其他状态；不要静默用空动作代替。
3. 确认多个外观如何分配 build、贴图或 prefab，不能假设一个已有 build 已经支持多个独立外观。
4. 先完成 G6，同版保留源工程与编译包，核对 `Asset("ANIM", "anim/<asset>.zip")`、bank/build、动作和方向。解包原版只作参考，不能当作原始作者骨架。
5. 验证编译成功后按明确接入范围替换资源与修改调用，再进游戏查实际尺寸、方向、脚底、伤害时刻和状态衔接。
6. 检查服务端、客户端和联机行为，查看日志，记录可复现问题。

### 7.1 游戏测试用例

先记录测试模组/资源哈希、游戏版本、世界与相机条件、个体 build、动画播放速率、实际移速和缩放。下列用例适用于最终交付；按“个体 x 四方向 x 用例”登记，主机本地与远端客户端的观察结果分别记录。P0 只做小样适用的子集，不能因此勾选全量用例。

| ID | 操作 | 通过条件 |
|---|---|---|
| T01 加载与身份 | 干净启动测试世界，生成每个目标个体，逐个转到四方向播放待机 | 正确 bank/build、比例、原点和个体外观；无缺图、错图、首帧闪烁及资源加载错误 |
| T02 行走与停步 | 每个方向连续走至少 5 个周期，再做至少 3 次启动/停止；记录每周期实际移动距离 | 支撑段足底相对地面稳定、步幅与实际移速匹配，抬脚和远近遮挡正确；待机与行走切换无根部跳位、末帧停顿。相机移动和场景投影须计入判断，不能只看原地视频 |
| T03 攻击与恢复 | 四方向各执行至少 3 次完整攻击，记录状态进入、可见接触、伤害调用与恢复时间 | 发力姿势与代码命中时间在预定误差内，伤害次数符合契约，无重复事件、脚掌翻转、内夹或攻击结束跳姿 |
| T04 攻击打断与受击 | 在蓄力、命中附近、恢复阶段分别施加普通受击或移动指令，记录 StateGraph 是否允许打断 | 实际打断或不打断行为符合代码；允许打断后无残余攻击事件、附件或异常脚姿。不允许打断不能强行判错，记录代码依据与观察结果 |
| T05 死亡与末姿 | 从待机、行走、攻击、受击状态触发致死，检查四方向及规定保持/移除时间 | 死亡正确接管状态，接地和末姿符合该项目规定的设计；身体不回弹、不自动回待机，层级/表情附件正确，后续事件符合死亡契约 |
| T06 转向与外观保持 | 在待机、行走及其他代码允许转向的状态连续切换四方向；按设计切换独立外观 | 正背面选择和侧面镜像正确，身份不串用，方向外贴图无残留，转向无意外位移或层级翻转 |
| T07 联机与重载 | 主机和至少一个远端客户端共同观察适用用例，重连/重载后复查身份与播放 | 两端资源、动作和外观符合契约；网络时差单列，不要求两端视频逐像素同步；客户端/主机日志没有新增相关错误 |

每条记录实际步骤、预期、实测、画面/日志路径和“通过 / 失败 / 待测 / 不适用”。不适用须有代码或范围依据；无远端客户端时 T07 写待测，不以主机画面替代。日志位置按当前系统和游戏版本确认，并在项目测试记录中写明，保留本次测试时间段。G7 要求所有适用用例及编译后游戏画面对照通过。

编译和游戏测试未完成时，按“阶段交付，最终交付未完成”记录，不把已有工程 ZIP 重新命名为已编译游戏动画包。
