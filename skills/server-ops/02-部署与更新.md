# 02 · 部署与更新

> 适用：把本机代码推到服务器上的 docker 项目（源码挂载模式）。本页流程已在 loomy-proxy 上实测通过
> （见 [07-踩坑与实测结论.md](07-踩坑与实测结论.md)）。

## 前置检查

1. 读 [services/<服务>.md](services/) 确认部署目录、源码目录、安装脚本与数据目录。
2. 本机代码是否已是想要的那份（`git status` / 未提交改动要不要一起上）。
3. 本机能跑通测试就先跑（如 `npm test`），别把坏代码推上去。
4. 备份：见 [04-备份与回滚.md](04-备份与回滚.md)。
5. 影响面与停机窗口：**任何 `restart` / `up -d` 都会影响依赖方**，先告诉用户再动手。

## 步骤

```bash
# 1) 本机打包（排除运行期数据与凭据；Windows 没有 rsync，用 tar）
cd <本地项目>
tar czf .deploy-tmp/<name>.tgz \
  --exclude=./.git --exclude=./node_modules --exclude=./data \
  --exclude=./secrets --exclude=./config/config.json --exclude=./.deploy-tmp .

# 2) 上传（scp 走 ssh 别名）
scp -q .deploy-tmp/<name>.tgz <别名>:/tmp/<name>.tgz

# 3) 服务器侧：解包 → 同步覆盖源码目录（--delete 让删掉的文件也生效）
ssh <别名> 'set -e; rm -rf /tmp/<name>-new && mkdir -p /tmp/<name>-new
  tar xzf /tmp/<name>.tgz -C /tmp/<name>-new
  rsync -a --delete /tmp/<name>-new/ <VPS_<服务>_SRC_DIR>/'

# 4) 校验代码真的换了（对比 md5，避免"以为部署了"）
ssh <别名> 'md5sum <VPS_<服务>_SRC_DIR>/src/cli.js'   # 与本机 md5sum 对比

# 5) 跑安装脚本（项目自带，幂等：不会覆盖 .env / config / data）
ssh <别名> 'cd <VPS_<服务>_SRC_DIR>/deploy && bash install.sh --network auto'
```

## 关键坑：源码挂载模式下 `up -d` 不会重新加载代码

安装脚本里的 `docker-compose up -d` 在 **compose 文件没变时不会重建容器**，进程里还是旧代码。
同步完源码必须显式重启：

```bash
ssh <别名> 'cd <VPS_<服务>_DEPLOY_DIR> && docker-compose restart'
# 或： docker-compose up -d --force-recreate <服务名>

# 等健康检查通过（最长 ~1 分钟）
ssh <别名> 'for i in $(seq 1 20); do s=$(docker inspect -f "{{.State.Health.Status}}" <容器> 2>/dev/null || echo none); echo "$s"; [ "$s" = healthy ] && break; sleep 3; done'
```

## 部署后

1. 按 [05-验证清单.md](05-验证清单.md) 分层验收。
2. 检查依赖方是否受影响（例如重启网关会让调用方出现一次 `transport error` 并临时降级，见服务档案）。
3. 清理：删服务器 `/tmp` 的临时包与脚本、删本机 `.deploy-tmp`（里头可能有明文凭据）。
4. 把本次的路径、命令、坑写进 `07-踩坑与实测结论.md` 或对应 `services/*.md`。

## 回滚

`app/` 只是源码副本，`data/` 不动就不会丢账号与密钥：

```bash
# 回到上一版本源码（保留一份旧 app/ 或重新同步旧 tag/commit），然后
ssh <别名> 'cd <VPS_<服务>_DEPLOY_DIR> && docker-compose restart'
```

数据回滚见 [04-备份与回滚.md](04-备份与回滚.md)。
