## 本机（Windows + MSYS）侧（2026-10-24 实测）

- **没有 `rsync`，也没有 `sshpass`**：推包只能 `tar` + `scp`，到服务器侧再 `rsync -a --delete`。
- 本机 `ssh` 可用，`~/.ssh/config` 里配了别名 + 密钥（`id_ed25519`）→ 一律用 `ssh <别名>`。
- MSYS 的 `/tmp` 与 Windows 版程序看到的路径**不是同一个**：给 node/python 脚本传临时文件路径时，
  用项目内目录（如 `.deploy-tmp/`），别用 `/tmp/…`，否则报 `ENOENT ... E:\tmp\...`。
- `scp` 多个文件可以用空格一次传（`scp a b <别名>:/tmp/`）。
- **Git Bash 会改写参数里的 POSIX 路径**：`--dest /www/x` 会变成 `E:/Program Files/Git/www/x`，
  `/tmp/x` 会变成 `C:/Users/…/AppData/Local/Temp/x`——传给原生程序（python/node 脚本）时尤其容易中招。
  处理：优先用 `MSYS_NO_PATHCONV=1 python scripts/server.py …`；`scripts/server.py` 自身也会识别并还原
  `/www/...` 与 `/tmp/...` 两类改写，认不出来时**直接报错**，不会静默用错路径。

## 源码挂载模式的部署（2026-10-24 实测）

- `docker-compose up -d` 在 **compose 文件内容没变时不会重建容器** → 同步完源码必须显式
  `docker-compose restart`（或 `up -d --force-recreate`），否则跑的还是旧代码。
- 判断"是否真的换上了新代码"用 **md5 对比**，不要只看时间戳或部署脚本的回显。
- 容器健康检查进入 `healthy` 大约需要 **10～30 秒**（有 `start_period`），别在 `starting` 阶段就断言失败。
- 安装脚本是幂等的：`.env`、`config/config.json`、`data/` 已存在就不覆盖——这正是数据能活下来的原因，
  但也意味着**改这些配置不会随部署生效**，要单独改。

## 数据一致性（2026-10-24 实测）

- 网关把 `data/accounts.json`、`data/keys.json` **整表读进内存**，之后每次写盘整表覆盖。
  服务在跑时用另一个进程（CLI / `docker exec`）改文件，**新增的账号会被内存快照抹掉**。
- 结论：**服务在跑 → 走管理 API / 管理台**；要跑 CLI 改数据 → 先停容器。
- 只读命令（`list`、`doctor`、`login --status` 等）随时可跑。

## 重启的连带影响（2026-10-24 实测）

- 重启网关会让依赖它的 sub2api 出现一次
  `openai.account_temp_unscheduled_transport ... connection refused`，
  并**把该账号临时降级 10 分钟**（期间表现为 `pool=0 / no available accounts`）。
- 自愈：`temp_unschedulable_until` 会到点自动清空（实测 00:04:56 报错 → 00:07:58 已恢复 → 00:09 起请求 200）。
- 手动兜底：`recover-state` + `schedulable=true`，见 [services/sub2api.md](services/sub2api.md)。
- 经验：**重启窗口内的失败是预期成本**，但必须在变更前把"会被影响的依赖方与降级时长"告诉用户。

## 账号/数据迁移（2026-10-24 实测）

- 本机存的是**掩码手机号**（`137****6487`），服务器可能是明文（`18055756347`）→
  比对必须按 `userid` → `id` → 「前 3 + 后 4 位」三级匹配，直接字符串相等会误判成"只在本地"。
- 迁移走管理 API 可以**零停机**，且新号会立刻进入调度；实测 6 个新号迁入后 20 秒内全部被真实调用成功。
- 同一个手机号在两侧可能有**两个不同的有效 session**（上游允许多会话）：
  保留"正在被调用"的那条，避免同一上游账号在池里占两格。

## 其他

- 服务器 `data/usage.jsonl` 会持续增长（1.4MB+ 量级），排查时用 `--since` / 只读尾部，别整文件打印。
- 引用带 `*` 的掩码手机号时注意 shell 通配符，必要时加引号。

## 加号：管理 API 短信登录（2026-10-24 实测）

- **不用停容器、也不用先建号**：`POST /admin/api/login/send-code {phone}` 发码 →
  用户报验证码 → `POST /admin/api/login/verify {loginId, code}`；**verify 自己就把账号落库**
  （响应带 `account` / `created`），不需要再调 `POST /admin/api/accounts`（那条要现成 session）。
- 实测时延：建号后**同一秒**就出现第一笔真实请求，15 分钟内该号被调用 16 次全部 `status=ok`
  → 新号零停机直接进调度。
- `verify` 不传 `name` 时后端自动起名（实测 `NK9765941`）；要固定名字就显式传 `name`。
- **配额坑**：`maxSendsPerHour=5` 同时按**手机号**与**来源 IP**各维护一个滑动小时窗；
  管理 API 的请求来源 IP 固定是 docker 网关（`172.21.0.1`）→ 走管理 API 发码时
  **所有手机号共享这 5 次/小时**，比「每号 5 次」更容易撞 `SEND_QUOTA_EXCEEDED`。
- 时序：验证码 300 秒有效（`codeTtlSeconds`）、pending 会话 900 秒、重发冷却 60 秒。
- 同一 `phone` / `userid` 再次登录**不会新增一条**，而是把原账号的 session 换新（`status` 回 `active`）
  ——这是刷新过期 session 的正确姿势，不要 DELETE 后重建。
- 全程零重启 → 依赖方 sub2api 无降级（实测变更后近 15 分钟 `unschedul|refused|transport` 计数为 0）。

## /add 加号页上线 + IP 直连实配真相（2026-10-24 实测）

- 部署 `/add` 独立加号页（手机号+验证码，移动端四步流程）后实测：`https://loomy.shuaichao.xyz/add` 200 可用；
  页面本身公开，但发码/验证 API 仍走 `/admin/api/login/*` 的管理鉴权（无凭据 401，已实测）。
- **模板 ≠ 实配**：`deploy/nginx/loomy-proxy.conf` 里的「IP 直连 server 块」（`server_name <IP>` :80）与 8788 备用端口块
  实际部署时只有 8788 块被带上，`server_name <IP>` 块没装 → `http://<IP>/` 落进宝塔默认站（404）。
- **8788 也用不了**：UFW 默认 DROP，规则里没放 8788（只放了 22/80/443/888/2053/8443 等）→ 即使 Nginx 监听了也进不来。
  要开 IP 直连需两步：vhost 加 `server_name <IP>` 块（80 已在 UFW 放行，只改 Nginx 即可）+ 云厂商安全组确认。
- 用户决策（2026-10-24）：不改 Nginx，统一走域名 HTTPS。
- 重启容器后 sub2api 出现一次 `account_temp_unscheduled_transport`（connection refused），降级窗口 = 报错时刻+10 分钟，
  与 sub2api.md 档案记载一致；恢复判据看请求 200，不是只看状态字段。
