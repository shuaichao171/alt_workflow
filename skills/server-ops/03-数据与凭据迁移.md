# 03 · 数据与凭据迁移

> 适用：把本机上的账号 / 密钥 / 配置搬到服务器，或在服务器上合并两份数据。
> 核心判断：**目标服务是否在跑**——在跑走管理 API，停着才改文件（见 SKILL.md「数据一致性陷阱」）。

## 0. 先算清差异，再决定动作

先把两边数据拉到本机临时目录比对（只读，不动生产）：

```bash
ssh <别名> 'cat <VPS_<服务>_DEPLOY_DIR>/data/accounts.json' > .deploy-tmp/srv-accounts.json
```

匹配顺序（本机常见的是**掩码手机号**，服务器可能是明文，别直接字符串相等）：

1. `userid`（最可靠）
2. 记录 `id`（同一网关内一致）
3. 手机号：数字位数不同时，用「前 3 位 + 后 4 位」比对（`180****6347` ↔ `18055756347`）

输出三张清单：**两侧都有 → 冲突**、**只在服务器**、**只在本机 → 待迁移**。

冲突处理原则（要用户拍板，别自己选）：

- 保留**正在被调用/更新**的那条（服务器侧统计与冷却状态更真实）；
- 两条都有效时，同一上游账号在池里占两格会造成统计分叉，一般保留一条；
- 替换正在服役的凭据前，必须先验证新凭据可用。

## 1. 服务在跑：走管理 API（推荐，零停机）

把待迁移数据整理成 JSON（**含明文凭据，用完立刻删**），在服务器上循环调用管理 API：

```python
# 服务器侧脚本骨架：密码只从 .env 读取，绝不打印
pw = next(l.split('=', 1)[1].strip() for l in open('<VPS_<服务>_DEPLOY_DIR>/.env')
          if l.startswith('LOOMY_PROXY_ADMIN_PASSWORD='))
req = urllib.request.Request('http://127.0.0.1:8787/admin/api/accounts',
                             data=json.dumps(item).encode(),
                             headers={'Content-Type': 'application/json',
                                      'Authorization': 'Bearer ' + pw})
```

- 本机整理载荷 → `scp` 上传到 `/tmp` → 服务器上 `python3` 跑循环 → 打印结果时**只输出 id/名称/状态**。
- 迁完补一次刷新（如 `POST /admin/api/points/refresh`、`POST /admin/api/models/refresh`），
  让新数据立刻进入调度。
- 最后 `rm` 掉服务器与本机的载荷文件。

## 2. 服务停着：改文件

```bash
ssh <别名> 'cd <VPS_<服务>_DEPLOY_DIR> && docker-compose stop'
# 备份 → 写文件（注意 600 权限与属主 root）→ 起容器
ssh <别名> 'cd <VPS_<服务>_DEPLOY_DIR> && docker-compose start'
```

写文件时保持原格式（缩进、末尾换行）与 `chmod 600`，否则服务可能拒绝读取或告警。

## 3. 凭据类文件

| 文件 | 说明 |
| --- | --- |
| `data/accounts.json` | 账号池（含 session，属"凭据"，绝不入库/进日志） |
| `data/keys.json` | 下游密钥（只存哈希/元数据时也按凭据对待） |
| `.env` | 环境变量，含管理台密码 |
| `secrets/*` | 上游 AK/SK 等，`chmod 600`，目录 700 |

迁移这些文件时：不要 `cat` 到终端、不要进提交、不要留在 `/tmp`。

## 4. 迁移后自检

1. 条数对不对（迁移前 N + 新增 M = 迁移后总数）。
2. 每条状态是不是 `active`，有没有 `cooling/invalid`。
3. 触发一次**真实调用**（见 [05-验证清单.md](05-验证清单.md)），确认新数据在调度里被用上。
4. 若迁移的是可领权益的新账号，确认权益动作是否按配置自动执行（幂等，可重跑）。
